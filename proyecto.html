El proyecto · agente ReAct para hls4ml

Un agente que explora diseños de FPGA sin sintetizarlos

01

El problema: sintetizar es lento, explorar exige muchas evaluaciones

Llevar una red neuronal a una FPGA con hls4ml exige sintetizarla para saber cuántos recursos (BRAM, DSP, FF, LUT) y cuánta latencia va a tener. Cada síntesis tarda minutos, y explorar el espacio de diseño (probar precisiones, reuse factors, estrategias y tamaños) exige decenas o cientos de ellas.

La tesis reemplaza la síntesis por un surrogate, un modelo entrenado sobre el dataset wa-hls4ml que predice las seis salidas en milisegundos, y lo pone en manos de un agente conversacional que el ingeniero usa en lenguaje natural.

Síntesis real (hls4ml + Vivado) 11.2 min
Surrogate 07D (local, CPU) 3.1 ms

Mediana sobre los mismos 140 diseños (ver Síntesis frente al surrogate y el agente). La barra del surrogate no se ve porque es unas 200,000 veces más corta.

1

Describir

Con una arquitectura completa o con una idea vaga («una red densa pequeña»). Si faltan datos, el agente parte de ejemplos reales.

2

Predecir y calificar

Recursos y latencia del 07D, con el nivel de confiabilidad medido para ese tipo de arquitectura (Dense, Conv1D o Conv2D).

3

Comparar y llevarse el reporte

Varios candidatos en una misma conversación, el mejor seleccionado y un reporte HTML autocontenido.

02

Cómo está armado el sistema

Dos agentes y un clasificador. Todo corre en local salvo el LLM, que es el único servicio externo. El surrogate se carga una sola vez en memoria y no depende de ninguna API.

04

Cómo razona: el bucle ReAct

ReAct (Reason + Act) alterna razonamiento y acción. El bucle, las herramientas y los límites son código; qué herramienta llamar, con qué argumentos y cuándo parar lo decide el LLM, guiado por el prompt de sistema.

Thought

El LLM escribe qué sabe y qué le falta: «el pedido trae bits y reuse factor global, puedo generar el candidato».

Action

Un único objeto JSON {"action": …, "action_input": {…}}. LangChain lo valida contra el esquema de la herramienta, inferido de la firma de la función.

Observation

El ejecutor corre la herramienta de verdad y le devuelve su salida. El LLM nunca inventa números: los lee de aquí.

Final Answer

Cuando ya llamó a las tres obligatorias, responde en español con recursos, latencia y confiabilidad.

Formato que escribe el LLM en cada vueltaSTRUCTURED_CHAT
Thought: El pedido especifica capas, bits y reuse factor global.
         Paso directo a traducirlo.
Action:
{
  "action": "generar_candidato",
  "action_input": { "pedido_usuario": "una red con dos capas densas…" }
}
Observation: Candidato generado y registrado con id=cnd_…

El flujo que pide el prompt

  1. Paso 0: si falta un solo dato (capas, bits o reuse factor global), la primera acción es sugerir_ejemplo_real.
  2. generar_candidato traduce el pedido a JSON.
  3. predecir_recursos con el candidate_id.
  4. estimar_baseline: la confiabilidad, siempre.
  5. generar_reporte: el entregable visual, siempre.

Si completó un valor que el usuario no dio, debe pasar por verificar_limites_operativos antes de predecir. Para comparar variantes, repite el flujo y cierra con seleccionar_mejor.

      07

      Lo que no se deja al LLM

      Cada vez que una regla importante dependía de que el modelo «se acordara», falló en alguna prueba. Esas reglas pasaron a código. Cada una nació de un hallazgo concreto.

      generar_candidato

      Compuerta de grounding

      Detecta con expresiones regulares si el pedido no dice los bits ni el reuse factor global. Si faltan y no se consultaron ejemplos reales, se niega a generar y pide sugerir_ejemplo_real.

      Por qué: tres intentos de reforzarlo solo con el prompt no cambiaron el comportamiento.
      callback del agente

      Recupera el pedido original

      Guarda lo que escribió el usuario. Si el agente resume el pedido y pierde datos que sí estaban, la herramienta traduce el original en vez de rechazar.

      Por qué: en los pilotos C2 y C3 el agente repetía el mismo resumen hasta agotar las iteraciones.
      ParserTolerante

      Lee solo la primera acción

      Descarta los bloques <think>, toma el primer JSON balanceado e ignora las Observation que el modelo invente después. Si no hay JSON, lanza un error para que reintente.

      Por qué: algunos backends ignoran stop y el modelo alucinaba la secuencia entera.
      ParserTolerante

      Repara llaves de cierre

      Si la acción solo quedó sin cerrar por llaves o corchetes faltantes al final, los completa y cuenta la reparación.

      Por qué: con arquitecturas largas el modelo repetía la misma llave de menos en cada reintento (piloto C2).
      estimar_baseline

      Degrada la confianza fuera de rango

      Si algún valor cae fuera del rango real del grupo, el nivel pasa a «limitada» aunque el R² histórico del grupo sea alto.

      Por qué: el Experimento E mostró la confianza fija con un reuse factor 10× fuera de todo valor real.
      main.py

      Reporte asegurado

      Si el agente termina sin llamar a generar_reporte, asegurar_reporte_mejor_candidato lo genera para el mejor candidato.

      Por qué: el entregable no debe depender de que el LLM se acuerde.
      generar_candidato

      Tres intentos de traducción

      Si la respuesta llega vacía o no se puede parsear, reintenta dentro de la herramienta. Si los tres fallan, registra el candidato como inválido.

      Por qué: en pedidos Conv largos el modelo a veces se quedaba en blanco al primer intento.
      llms/clients.py

      Límites de tiempo

      90 s por llamada al LLM y un tope de tiempo total para cada agente (360 s el de predicción).

      Por qué: con streaming, el timeout por llamada no corta una respuesta que llega lenta.

      09

      El surrogate 07D, la herramienta que predice

      Un transformer de dos ramas con fusión tardía (Two-Branch Late Fusion), 1,728,967 parámetros, entrenado sobre 433,676 diseños. Recibe la arquitectura canónica y devuelve las seis salidas.

      Rama global Configuración del modelo

      strategy y 17 variables numéricas (3 de base y 14 derivadas físicas)

      2 bloques transformer
      Rama de capas Hasta 55 capas

      Por capa: tipo, padding y activación; 19 numéricas (formas, filtros, kernel, reuse factor, bits); use_bias y activación cuantizada

      4 bloques transformer
      fusión por cross-attention
      Cabeza multitarea
      BRAMDSPFFLUTciclosII

      Más una compuerta que decide si DSP = 0 (umbral 0.50).

      d_model 192 · 8 cabezas · d_ff 256 · dropout 0.05 · PyTorch en CPU

      Límites conocidos del sistema base

      • seleccionar_mejor recibe un criterio en texto pero hoy lo ignora: ordena siempre igual.
      • evaluar_restricciones solo revisa el formato, no las restricciones de recursos del usuario.
      • BRAM sale con advertencia de sanidad en Conv1D y Conv2D en el smoke test.
      • La verificación del 7 nov es una corrida por familia: prueba que funciona, no mide calidad.
